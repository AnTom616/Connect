      Objetivo do projeto

      O ConnectHub é um painel administrativo desenvolvido com finalidade acadêmica para demonstrar, de ponta a ponta, como construir um sistema de gerenciamento de cadastros (CRUD) com arquitetura profissional e persistência real de dados. O projeto cobre desde a interface responsiva até as funções de servidor e o banco de dados, seguindo boas práticas de separação de responsabilidades.

      Todas as informações exibidas — contadores do dashboard, listagens, resultados de busca e datas — são calculadas exclusivamente a partir dos registros efetivamente armazenados no banco de dados. Não existe nenhum dado fictício simulado no código da interface: se o banco está vazio, os indicadores mostram zero e a tela apresenta um estado vazio orientado ao usuário.

      Tecnologias utilizadas

      HTML5

      Estrutura semântica das três telas, modais acessíveis e componentes reutilizáveis.

      CSS3

      Tema Modern Dark Dashboard com variáveis customizadas, Grid e Flexbox, animações leves e layout responsivo.

      JavaScript

      Aplicação sem frameworks: roteamento por hash, requisições fetch, máscara de telefone, validação e toasts.

      Vercel Functions

      Funções serverless em Node.js responsáveis pela API REST (rota /api) que executa as operações no banco.

      PostgreSQL · Neon

      Banco relacional gerenciado, integração oficial do Marketplace da Vercel, usado em produção via DATABASE_URL.

      SQLite (dev local)

      Driver de desenvolvimento sem configuração, com exatamente a mesma interface do driver Postgres.

      Como o CRUD funciona

      Create

      O botão “Novo Cadastro” abre um modal que valida os campos (nome completo, e-mail, telefone com máscara e cidade) e envia os dados por POST /api/cadastros. O servidor revalida tudo, impede e-mails duplicados e grava o registro com ID (UUID) e data de cadastro gerados automaticamente pelo banco.

      Read

      A tabela e o dashboard consomem GET /api/cadastros e GET /api/estatisticas. A busca por nome, e-mail ou cidade, a ordenação por nome ou data e a paginação são executadas diretamente no banco de dados — não no navegador — garantindo desempenho e indicadores reais.

      Update

      O ícone de edição recarrega o registro (GET /api/cadastros/:id), preenche o modal e envia as alterações por PUT /api/cadastros/:id. O e-mail continua único e a listagem é atualizada imediatamente após a resposta do servidor.

      Delete

      A exclusão exige confirmação em um modal próprio com destaque vermelho. Confirmada, envia DELETE /api/cadastros/:id e o registro é removido do banco. Qualquer falha é reportada por um toast de erro e a linha permanece na tela.

      Arquitetura e persistência de dados

      A aplicação é organizada em camadas independentes. A interface nunca fala com o banco diretamente: ela apenas consome a API REST, que por sua vez delega toda leitura e escrita à camada de acesso a dados (o padrão repositório). Assim, trocar o provedor de armazenamento não exige alterar nenhuma linha do frontend.

      Por que arquivos locais não servem na Vercel? As funções serverless rodam em um ambiente efêmero: o sistema de arquivos é somente leitura (exceto /tmp, descartado a cada execução) e cada requisição pode ser atendida por uma instância diferente. Gravar em disco, usar arrays em memória ou localStorage — que vive apenas no navegador de cada visitante — significaria perder dados silenciosamente. Por isso a persistência é feita em um banco gerenciado: o Neon Postgres, conectado pela variável de ambiente DATABASE_URL.

      Publicação na Vercel

      1. Crie um banco gratuito no Neon e copie a connection string (pooled);
      2. Hospede o projeto no GitHub e importe o repositório na Vercel;
      3. Em Settings → Environment Variables, cadastre DATABASE_URL;
      4. Faça o deploy — o schema da tabela é criado automaticamente na primeira requisição;
      5. Verifique o selo “Banco conectado” no cabeçalho e teste o CRUD completo.

      O guia completo, com alternativas de banco, variáveis de ambiente e checklist de testes pós-deploy, está documentado no arquivo README.md do projeto.
